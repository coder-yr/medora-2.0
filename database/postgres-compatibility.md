# Medora 2.0 — PostgreSQL & Supabase Compatibility Analysis

## 1. Executive Summary
This document provides an in-depth technical analysis of 18 architectural and SQL dialect differences between the legacy ICTHospital MariaDB/MySQL/SQLite schema and the approved target platform: **Supabase PostgreSQL** managed via **Prisma ORM**.

Every incompatibility includes source evidence, PostgreSQL runtime behavior, recommended compatibility strategy, required tests, and flags for owner decisions.

---

## 2. In-Depth Dialect & Compatibility Analysis

### 1. AUTO_INCREMENT Identifiers & Sequence Behavior
- **Legacy Source & Behavior**:
  - Legacy Laravel migrations use `$table->increments('id')` or `$table->id()`, which generate MySQL `INT/BIGINT AUTO_INCREMENT` or SQLite `INTEGER PRIMARY KEY AUTOINCREMENT`.
- **PostgreSQL Difference**:
  - PostgreSQL uses sequences (`BIGSERIAL` or SQL:2003 standard `BIGINT GENERATED BY DEFAULT AS IDENTITY`). Sequences do not automatically reset or re-index upon row deletions, and sequence caches must be synchronized after manual ID insertions during data migration.
- **Proposed Mapping**:
  - Define primary keys in Prisma as `id BigInt @id @default(autoincrement())` or `Int @id @default(autoincrement())`.
  - For Phase 6 data migration, create a post-migration SQL script:
    ```sql
    SELECT setval(pg_get_serial_sequence('patient', 'id'), COALESCE(MAX(id), 1)) FROM "patient";
    ```
- **Required Tests**: Verify that inserting new records after importing historical IDs does not collide with sequence state.
- **Owner Decision Needed**: Confirmation whether integer sequences are preferred over UUIDs for primary keys during initial migration.

---

### 2. BIGINT versus UUID Decisions
- **Legacy Source & Behavior**:
  - All foreign keys (`payment_id`, `patient_id`, `doctor_id`, `bed_id`) store integer values (often coerced into `VARCHAR(100)` or `INT`).
- **PostgreSQL Difference**:
  - PostgreSQL supports native `UUID` (`gen_random_uuid()` or UUIDv7). UUIDs prevent enumeration attacks and simplify distributed syncing, but converting existing tables to UUID breaks legacy external references (e.g. printed barcode cards, lab slip numbers).
- **Proposed Mapping**:
  - **Retain `BigInt` / `Int` primary keys** for core entities (`patient.id`, `appointment.id`, `payment.id`) to preserve exact parity with legacy printed records, receipts, and lab samples.
  - Add an optional `uuid String @default(uuid()) @unique` column for modern API exposition and public-facing URL slugs.
- **Required Tests**: Benchmark query performance and foreign key join times between BigInt and UUID fields.
- **Owner Decision Needed**: Approve retaining BigInt primary keys with secondary UUIDs versus complete UUID transition.

---

### 3. VARCHAR Columns Containing Numeric Values
- **Legacy Source & Behavior**:
  - Multiple financial and operational columns were created as `VARCHAR`:
    - `payment.gross_total`, `payment.amount_received`, `payment.discount`
    - `pharmacy_payment.gross_total`, `pharmacy_payment.amount_received`
    - `medicine.price`, `medicine.box`, `medicine.s_price`
    - `patient.patient_id` (zero-padded numeric string `000001`)
  - Legacy queries perform inline arithmetic via SQL casting:
    `CAST(COALESCE(NULLIF(payment.gross_total, ""), "0") AS DECIMAL(15,2))`
- **PostgreSQL Difference**:
  - PostgreSQL strictly enforces strong typing. Executing arithmetic, comparisons, or aggregate functions (`SUM`, `AVG`) on `VARCHAR` columns throws `ERROR: operator does not exist: character varying + numeric`.
- **Proposed Mapping**:
  - Map all monetary values in Prisma to `Decimal @db.Decimal(12, 2)`.
  - Map stock quantities to `Int`.
  - Retain `patient.patient_id` as `String @db.VarChar(20)` since it represents a formatted code with leading zeros (`000001`).
- **Required Tests**: Ingestion test passing empty strings `""`, `NULL`, and formatted strings `"1,250.00"` through Prisma parsing filters.
- **Owner Decision Needed**: None (Standardized best practice).

---

### 4. DECIMAL / NUMERIC Precision & Rounding Semantics
- **Legacy Source & Behavior**:
  - `Billing.php` and `ShareCalculator.php` use PHP `round($val, 2)` and format with `number_format($val, 2, '.', '')`.
  - An epsilon of `0.004` is hardcoded in `Billing::isPaid()`: `balance <= 0.004`.
- **PostgreSQL Difference**:
  - PostgreSQL `DECIMAL(12, 2)` uses exact fixed-point arbitrary precision arithmetic (half-away-from-zero rounding on `ROUND()`), avoiding binary floating-point representation inaccuracies.
- **Proposed Mapping**:
  - In NestJS, utilize `decimal.js` or Prisma `Prisma.Decimal` for all line item multiplications, commission splits, and invoice balances.
  - Maintain the `0.004` tolerance for settlement classification to ensure legacy invoices migrate cleanly without status flips.
- **Required Tests**: Financial unit test comparing doctor revenue share base amounts across 1,000 synthetic multi-line invoices.

### 5. DATE, DATETIME, Timestamp, and Timezone Semantics
- **Legacy Source & Behavior**:
  - Legacy MySQL uses `DATETIME` or stores dates as unstructured strings (`VARCHAR(100)` in `appointment.date`, `payment.date`).
  - No timezone offsets were stored; the server assumed local system time (`Asia/Karachi` or `UTC`).
- **PostgreSQL Difference**:
  - PostgreSQL provides `TIMESTAMPTZ` (stored in UTC) and `DATE` (calendar date without time). `TIMESTAMP WITHOUT TIME ZONE` can cause ambiguous query filters when accessed from clients in different timezones.
- **Proposed Mapping**:
  - Event timestamps (`created_at`, `updated_at`, `closed_at`, `started_at`) $\rightarrow$ `DateTime @db.Timestamptz`.
  - Calendar dates without time components (`birthdate`, `holiday.date`) $\rightarrow$ `DateTime @db.Date`.
  - OPD clinic hours (`start_time`, `end_time`) $\rightarrow$ `String @db.VarChar(5)` (`HH:mm`).
- **Required Tests**: Verify that appointments booked across Daylight Saving Time transitions or UTC offsets display on the exact local calendar day.
- **Owner Decision Needed**: Confirm the canonical hospital base timezone (e.g. `Asia/Karachi`, UTC+5) for legacy historical date conversion.

---

### 6. Zero Dates (`0000-00-00`) and Invalid Date Strings
- **Legacy Source & Behavior**:
  - In older MySQL non-strict modes, uninitialized date fields default to `0000-00-00` or `0000-00-00 00:00:00`.
- **PostgreSQL Difference**:
  - PostgreSQL rejects zero dates with `ERROR: date/time field value out of range: "0000-00-00"`.
- **Proposed Mapping**:
  - Data migration ETL pipeline must sanitize dates:
    ```sql
    CASE WHEN date = '0000-00-00' OR date = '' THEN NULL ELSE date::date END
    ```
- **Required Tests**: Profile historical date columns with `database/scripts/profile-data-quality.php`.

---

### 7. BOOLEAN Representation & Truthiness
- **Legacy Source & Behavior**:
  - MySQL stores booleans as `TINYINT(1)` (`0` or `1`).
  - Legacy tables also store text flags: `permission.permission_type = 'yes'|'no'`, `patient_type.active = 1|0`.
- **PostgreSQL Difference**:
  - PostgreSQL has a native `BOOLEAN` type (`TRUE`, `FALSE`, `NULL`). Comparing boolean columns against integers (`WHERE active = 1`) fails without explicit casting.
- **Proposed Mapping**:
  - Prisma models define active flags as `Boolean @default(true)`.
  - Permissions map `permission_type` to a clean boolean `granted Boolean @default(false)` in Medora 2.0.
- **Required Tests**: Test that Prisma boolean queries generate valid PostgreSQL `WHERE "active" = true` clauses.

---

### 8. JSON Fields & PostgreSQL JSONB Suitability
- **Legacy Source & Behavior**:
  - Consult templates (`consult_template.template_data`) and legacy notification settings store serialized PHP strings or raw JSON text in `TEXT` columns.
- **PostgreSQL Difference**:
  - PostgreSQL `JSONB` stores decomposed binary JSON with indexability (`GIN` indexes) and containment operators (`@>`, `?`).
- **Proposed Mapping**:
  - Map `consult_template.template_data` and audit log changes to `Json @db.JsonB`.
- **Required Tests**: Validate serialization and deserialization of consultation templates in NestJS DTOs.

---

### 9. Case Sensitivity, Collation & Text Comparisons
- **Legacy Source & Behavior**:
  - MySQL default collation `utf8mb4_unicode_ci` performs case-insensitive searches by default (`WHERE login = 'admin'` matches `'Admin'`).
- **PostgreSQL Difference**:
  - PostgreSQL standard collations are case-sensitive (`WHERE login = 'admin'` will NOT match `'Admin'`).
- **Proposed Mapping**:
  - For user authentication logins and emails, enforce lowercase normalization in NestJS before query execution (`login.toLowerCase().trim()`).
  - For clinical search queries (patient search by name or CNIC), use Prisma's `mode: 'insensitive'` (which generates `ILIKE` in PostgreSQL) or configure the `citext` extension.
- **Required Tests**: Feature test verifying that typing `john doe` in patient search finds records stored as `John Doe`.

---

### 10. MySQL-Specific SQL & Non-Strict `GROUP BY` Behavior
- **Legacy Source & Behavior**:
  - Legacy queries in reporting controllers (e.g. `AccountingController`, `ReportController`) include columns in the `SELECT` list that are neither aggregated nor included in `GROUP BY`.
- **PostgreSQL Difference**:
  - PostgreSQL strictly adheres to ANSI SQL: every non-aggregate column in the `SELECT` clause must appear in the `GROUP BY` clause. Violations throw `ERROR: column "..." must appear in the GROUP BY clause or be used in an aggregate function`.
- **Proposed Mapping**:
  - Re-author reporting queries using Prisma aggregate APIs (`groupBy`, `_sum`, `_count`) or strict raw SQL window functions.
- **Required Tests**: Execute all financial reporting queries against a PostgreSQL test container.

---

### 11. String Truncation & Strict Length Enforcements
- **Legacy Source & Behavior**:
  - In legacy MySQL non-strict modes, strings exceeding column lengths are silently truncated without error.
- **PostgreSQL Difference**:
  - PostgreSQL aborts transactions with `ERROR: value too long for type character varying(n)`.
- **Proposed Mapping**:
  - In Prisma, specify realistic bounds (e.g. `VarChar(255)` instead of `VarChar(20)` where clinical notes or descriptions may expand) or use unbounded `String @db.Text` for notes and observations.
  - Enforce input length validation in NestJS using `class-validator` (`@MaxLength(n)`).
- **Required Tests**: Input boundary validation tests submitting strings of length `N+1`.

---

### 12. Foreign-Key Integrity & Uniqueness Enforcements
- **Legacy Source & Behavior**:
  - As discovered in `database/scripts/inspect-schema.php`, the legacy SQLite database contains **0 foreign key constraints**. Relationships were purely logical.
- **PostgreSQL Difference**:
  - PostgreSQL enforces referential integrity strictly. Inserting an `appointment` with `patient = 99999` fails if patient `99999` does not exist.
- **Proposed Mapping**:
  - Phase 3 Prisma schema models explicit relationships with `@relation(fields: [...], references: [id])`.
  - Phase 6 data cleansing scripts must identify and nullify or quarantine orphan records before applying foreign key constraints.
- **Required Tests**: Orphan detection scripts (`database/scripts/profile-data-quality.php`) executed prior to schema generation.

---

### 13. Soft-Delete Semantics (`deleted_at`)
- **Legacy Source & Behavior**:
  - Laravel Eloquent utilizes the `SoftDeletes` trait, adding `WHERE deleted_at IS NULL` to queries automatically.
- **PostgreSQL Difference**:
  - PostgreSQL has no native concept of soft-deletes; it must be implemented via application logic, view layers, or Prisma client extensions. Unique constraints on soft-deleted tables (e.g. unique username) collide if historical deleted rows retain the same value.
- **Proposed Mapping**:
  - Implement a Prisma Client extension in NestJS that automatically filters `deletedAt: null`.
  - For unique constraints on soft-deleted entities (e.g. `hospital_branch.code`), use PostgreSQL partial unique indexes:
    ```sql
    CREATE UNIQUE INDEX uq_branch_code ON hospital_branch(code) WHERE deleted_at IS NULL;
    ```
- **Required Tests**: Verify that soft-deleted branches do not appear in active queries and that branch codes can be reused after soft deletion.

---

### 14. Transactions & Pessimistic Row-Level Locking (`SELECT FOR UPDATE`)
- **Legacy Source & Behavior**:
  - Legacy Laravel uses `DB::transaction()` with Eloquent `lockForUpdate()` across 5 critical paths:
    1. Appointment double-booking check
    2. Bed admission mutual exclusivity
    3. Patient ID sequence allocation
    4. Pharmacy stock decrement
    5. Invoice payment settlement
- **PostgreSQL Difference**:
  - PostgreSQL supports `SELECT ... FOR UPDATE` and `SELECT ... FOR NO KEY UPDATE` with fine-grained row lock escalation.
  - Prisma's high-level fluent API does not expose native row locks; interactive transactions (`prisma.$transaction(async (tx) => { ... })`) with raw query row-locks or serializable isolation are required.
- **Proposed Mapping**:
  - In NestJS services, execute concurrency-critical reads using Prisma interactive transactions with raw locking:
    ```typescript
    await tx.$queryRaw`SELECT id FROM "bed" WHERE id = ${bedId} FOR UPDATE`;
    ```
- **Required Tests**: High-concurrency test simulating 20 simultaneous bookings for the same appointment slot.

### 15. Patient ID Generation Concurrency
- **Legacy Source & Behavior**:
  - Uses `SELECT MAX(CAST(patient_id AS UNSIGNED)) AS n FROM patient FOR UPDATE` to compute the next 6-digit zero-padded number (`000042`).
- **PostgreSQL Difference**:
  - Casting string to integer in PostgreSQL requires `CAST(patient_id AS INTEGER)`. If any alphanumeric or corrupt string exists in `patient_id`, PostgreSQL throws a conversion error.
- **Proposed Mapping**:
  - Create a dedicated PostgreSQL sequence for MR numbers:
    ```sql
    CREATE SEQUENCE patient_mr_seq START 1;
    ```
  - Generate the formatted identifier in NestJS: `String(nextVal).padStart(6, '0')`. This is lock-free, atomic, and immune to alphanumeric string collision.
- **Required Tests**: Concurrent patient registration test creating 50 patients simultaneously.

---

### 16. Appointment & Bed Allocation Concurrency
- **Legacy Source & Behavior**:
  - `AppointmentController` checks boundary overlap:
    `s_time < new.e_time AND e_time > new.s_time`
  - `AdmissionController` checks active occupancy: `d_time IS NULL`.
- **PostgreSQL Difference**:
  - PostgreSQL provides native range types (`tstzrange`) and GiST exclusion constraints (`EXCLUDE USING gist (...)`), which can prevent temporal overlaps entirely at the database engine level without application-level locking.
- **Proposed Mapping**:
  - Medora 2.0 can maintain application-level interactive transactions initially, with the option to enforce PostgreSQL exclusion constraints on `(doctor_id, tstzrange(start_time, end_time))`.
- **Required Tests**: Double-booking collision test attempting simultaneous overlapping slot reservations.

---

### 17. Pharmacy Stock Decrement Atomicity
- **Legacy Source & Behavior**:
  - Decrements `medicine.quantity` in a loop; throws validation exception if `$item->quantity < $requested`.
- **PostgreSQL Difference**:
  - Handled identically inside an ACID transaction, or protected with a database-level `CHECK (quantity >= 0)` constraint.
- **Proposed Mapping**:
  - Add a database constraint: `ALTER TABLE medicine ADD CONSTRAINT chk_stock_non_negative CHECK (quantity >= 0);`
  - This guarantees that stock can never drop below zero even if application logic encounters a race condition.
- **Required Tests**: Attempting to sell 15 units when stock is 10 must fail with a transaction rollback.

---

### 18. Invoice & Payment Balance Updates
- **Legacy Source & Behavior**:
  - Derives status (`paid`, `part paid`, `unpaid`) dynamically by summing child `invoice_payment` records and comparing against header `gross_total`.
- **PostgreSQL Difference**:
  - PostgreSQL handles concurrent payments cleanly under row-locking.
- **Proposed Mapping**:
  - Lock the parent invoice row (`FOR UPDATE`) when appending payment transactions.
  - Recalculate balance atomically inside the transaction.
- **Required Tests**: Concurrent payment test simulating two cashiers attempting to settle the final $50 of an invoice simultaneously.
